Step 3

Set up memory and context

EasyIntermediateHard

The dashboard only stays consistent month to month if Claude remembers the definitions, sources and design decisions you settled on. Write them down once, in a place Claude reads every time.

Create a Claude Project for the dashboard

  1. In Claude, create a new Project named after the page, for example Reliability Strategy Dashboard.
  2. Paste the instruction template on the right into the project's Instructions and fill in the blanks.
  3. Add supporting files to project knowledge: KPI definitions, the metric glossary, a screenshot of a page you want to match, and the current .jsx file if you already have one.
  4. Start every dashboard chat inside this project. Claude will read the instructions before it writes anything.
Memory: with memory turned on, tell Claude explicit facts you want kept across chats, such as "Remember that my Gizmos app is relstrat in the telus org and the source workbook is Churn Measurement 2026." Ask "what do you remember about my dashboard?" to check.
Claude Code: the same information belongs in the repository as a CLAUDE.md file at the root, next to the README. Claude Code reads it on every session. Keep the build and deploy commands there too.

Step 4

Sign in to telus.gizmos.run and set up your app

EasyIntermediateHard

Gizmos is the TELUS hosting platform for internal web apps. Every app gets its own address, sits behind TELUS SSO, keeps a version history, and can be shared with named people or the whole organization.

First sign-in

  1. Open telus.gizmos.run and sign in with your TELUS account. The hub lists the apps you own and the ones shared with you.
  2. Note the org slug: telus. Your app will live at <app-name>.telus.gizmos.run, with a hub page at telus.gizmos.run/live/<app-name>.
  3. Decide a name now. Names are lowercase letters, numbers, dashes and underscores, 1 to 64 characters, no dots or spaces. Names like admin, api, hub, dev, studio and settings are reserved. Deleting an app forfeits its name for good.
Example
The Reliability Strategy dashboard is the app relstrat, live at relstrat.telus.gizmos.run.

Settings worth knowing

Visibility
New apps are private. Share with named TELUS emails as viewer, editor or admin, or set organization so anyone at TELUS with SSO can open it. Organization visibility runs a quick health check on the home page first.
Versions
Every publish creates a version. Roll back or make a saved but unpublished version live from the Versions tab.
Description and labels
One line under 160 characters and up to five labels. They show on the community list, so write for someone searching for your KPI.
Favicon
Include a favicon.ico in what you upload and the tab, bookmark and hub avatar pick it up.
API key
Generate a gzm_ key at gizmos.run/settings. It is only needed for the Hard route. Store it as a GitHub secret. Never paste it into a chat, a file or a commit.

Artifacts vs permanent apps (Intermediate route)

When Claude deploys through the connector, it creates a Gizmos Artifact: a disposable app with a name like art-3f9c... and a 7 day lease. Every update from Claude renews the lease. If nobody updates it for 7 days it is deleted, and there is a further 7 day window where a new deploy restores it.

For KPI tracking you want it permanent. Open the artifact in the hub and promote it, choosing a real name at the same time. From then on it behaves like any other app. Promotion happens once; updates keep working.

Renaming breaks old links. Promoting with a new name stops the old art-... address immediately. Promote before you share the link widely, or share only the final name.

Step 5

Set up or reuse data sources

EasyIntermediateHard

Claude builds the page from whatever you point it at. A tidy Google Sheet is the most reliable source: it is shared, versioned, easy to review, and the Drive connector reads it directly. Keep numbers in Sheets and narrative in Docs.

Shape the workbook so Claude reads it cleanly

  • One tab per table. The Reliability Strategy dashboard reads three tabs of the Churn Measurement 2026 workbook: the KPI table, the Looker ticket categories per product, and the initiatives list.
  • Months across, metrics down. A single header row with month labels like Jan 2025. No merged cells, no blank spacer columns, no totals hidden inside the data range.
  • Blank means not reported. Leave future or lagging months empty rather than typing 0. Churn reported two months behind stays blank and the page shows it as not yet available.
  • A definitions tab. Metric name, formula, source system, owner. Claude uses it for tooltips and footnotes.
  • Share the sheet with the people who will run updates, so their Drive connector can read it too.

Step 6

Set up GitHub for the automated route

Hard

On this route the repository is the source of truth and GitHub Actions does the publishing. You set up the repo, one secret and one workflow file. After that, publishing is a side effect of merging.

  1. Create the repository

    Create a private repo in the TELUS GitHub organization (or your own account if that is the norm on your team). Add a README. Default branch main.

  2. Connect it to Claude Code

    Go to claude.ai/code, connect GitHub, and install the Claude GitHub App on the repository. Create an environment for the repo if prompted. Claude Code will clone it into a fresh session each time.

  3. Add the API key as a secret

    In the repo, open Settings, then Secrets and variables, then Actions. Create a repository secret named GIZMOS_API_KEY with the gzm_ key from step 4. The workflow reads it from there; it never appears in logs.

  4. Scaffold the site

    Ask Claude Code to turn your App.jsx into a small Vite project under site/: an index.html, a main.jsx that mounts App, a vite.config.js with base: "./", and a package.json with a build script. Vite projects must be built before they are pushed to Gizmos; the platform does not run JSX or bundler plugins for you.

  5. Add the deploy workflow

    Save the file below as .github/workflows/deploy-gizmos.yml. It runs on every push to main that touches site/, and on demand from the Actions tab where you can choose publish (go live) or save (store a version without publishing).

    .github/workflows/deploy-gizmos.yml
    name: Deploy to Gizmos

on:
  push:
    branches: [main]
    paths: ["site/**", ".github/workflows/deploy-gizmos.yml"]
  workflow_dispatch:
    inputs:
      publish:
        description: "Publish (go live) or only save a version"
        type: choice
        options: [publish, save]
        default: publish

concurrency:
  group: deploy-gizmos
  cancel-in-progress: false

jobs:
  deploy:
    runs-on: ubuntu-latest
    env:
      GIZMOS_URL: https://gizmos.run
      GIZMOS_APP: your-app-name      # change me
      GIZMOS_ORG: telus
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
          cache-dependency-path: site/package-lock.json

      - name: Install dependencies
        working-directory: site
        run: npm ci

      - name: Build
        working-directory: site
        run: npm run build

      - name: Install gizmos CLI
        run: |
          curl -fsSL https://gizmos.run/skills/install.sh | bash
          echo "$HOME/.local/bin" >> "$GITHUB_PATH"

      # The CLI lists files with `git ls-files`, so a gitignored dist/
      # inside the checkout yields "No files found". Push from a copy
      # that lives outside the repository instead.
      - name: Stage build output outside the repository
        run: |
          rm -rf "$RUNNER_TEMP/deploy"
          cp -r site/dist "$RUNNER_TEMP/deploy"
          echo "DEPLOY_DIR=$RUNNER_TEMP/deploy" >> "$GITHUB_ENV"

      - name: Preview upload
        run: gizmos push --dry-run --app "$GIZMOS_APP" --org "$GIZMOS_ORG" "$DEPLOY_DIR"

      - name: Deploy (go live)
        if: github.event_name == 'push' || inputs.publish == 'publish'
        env:
          GIZMOS_API_KEY: ${{ secrets.GIZMOS_API_KEY }}
        run: gizmos push --app "$GIZMOS_APP" --org "$GIZMOS_ORG" -m "${GITHUB_REF_NAME} ${GITHUB_SHA::7}" "$DEPLOY_DIR"

      - name: Save version only (not live)
        if: github.event_name == 'workflow_dispatch' && inputs.publish == 'save'
        env:
          GIZMOS_API_KEY: ${{ secrets.GIZMOS_API_KEY }}
        run: gizmos save --app "$GIZMOS_APP" --org "$GIZMOS_ORG" -m "${GITHUB_REF_NAME} ${GITHUB_SHA::7}" "$DEPLOY_DIR"

  6. Merge and watch the Actions tab

    Push the workflow to main. Open the Actions tab and watch the run. The Preview step lists the files that will be uploaded; the Deploy step prints the live URL. The first successful run creates the app in Gizmos under the name you set.

!
Lesson learned: "No files found to deploy". The first version of the Reliability workflow pushed site/dist straight from the checkout. Because dist/ is gitignored and the CLI collects files with git, it uploaded nothing. Copying the build to the runner's temp folder fixed it. The workflow above already includes that fix.
i
Always name the org. A push defaults to the key owner's primary org. Passing --org telus every time means the app never lands in the wrong place if your account belongs to more than one org.

Step 7

Set up the Tableau connector

Optional, all routes

If a KPI already exists as a Tableau view, you do not need to re-export it by hand each month. The Tableau Cloud connector lets Claude find the workbook, read the view's data and drop it into your sheet or straight into the dashboard.

Connect once

  1. In Claude, open Settings, then Connectors, and add Tableau Cloud from the TELUS directory.
  2. Sign in with your TELUS account and approve the consent screen. Claude gets the same access you have in Tableau, nothing more.
  3. Test it: ask Claude to list my Tableau workbooks or search Tableau for "CCT Mapping". You should see workbook names, projects and views.

What Claude can do with it

Find
Search content, list projects, workbooks, views and data sources.
Read
Get a view's underlying data as a table, or run a query against a published data source with filters and aggregations.
Snapshot
Fetch a view image for a static screenshot in a summary.
Pulse
Read Pulse metric definitions and insights for narrative context.

Two ways to use the data

Recommended
Land it in the sheet. Ask Claude to pull the view data and write it into a dedicated tab of your workbook (for example Tableau DRD extract). The dashboard reads the sheet like everything else, the numbers are reviewable, and the monthly loop stays the same.
Quick
Read it straight into the page. Ask Claude to query the view and update the DATA block directly. Faster, but there is no paper trail between Tableau and the page.
Prompt
Find the "DRD Assure CCT Mapping" view in Tableau. Pull its data for the
last 18 months grouped by product and ticket category, and write it into
a new tab called "Tableau DRD extract" in the Churn Measurement 2026
workbook, months across. Then tell me the row counts per product.
i
From experience. The Reliability dashboard first took its ticket-driver breakdown from the Tableau DRD feed, then moved to Looker category tabs maintained inside the workbook because the categories were stable and easier to reconcile. Tableau is a great feed. The sheet is still the record.

Step 8

Build and publish

With the setup done, this is the part you repeat. Each route below shows the flow, the exact steps, and what "done" looks like.

  1. Ask for a single file

    Inside your Project, ask Claude to build the dashboard as one React file named App.jsx with a default export. That is the same shape as the React artifacts Claude shows in chat, so you can preview it in the side panel before you download it.

  2. Review in the chat preview

    Check numbers against the sheet, click through the pages, and test on a narrow window. Iterate until it is right. Ask Claude to fix anything before you download.

  3. Download App.jsx

    Use the download control on the artifact. If Claude produced index.html and other assets too, download them all and keep the folder structure.

  4. Upload in the Gizmos hub

    At telus.gizmos.run choose Deploy (or New app), enter your app name, and upload the file or folder. The hub accepts uploads up to 10 MB. Add a description and a favicon if you have one, then publish.

  5. Share the link

    Open <app-name>.telus.gizmos.run, confirm it renders, and set visibility or add viewers. Bookmark the hub page: it is where you will upload the next version.

Updating later: return to the same app in the hub and upload the new file. The previous version stays in the Versions tab, so a bad upload is one click away from a rollback.

  1. Build as usual

    Same as the Easy route: ask for the page inside your Project and review the preview.

  2. Ask Claude to deploy it

    Say "Deploy this to Gizmos". Claude calls the connector's deploy_artifact tool with the files and returns a live link under telus.gizmos.run. No API key, no download.

  3. Keep the artifact name

    The result names the artifact (something like art-3f9c1b...) and the org. Claude needs both to update the same page later. Ask Claude to remember them, and paste them into your project instructions.

  4. Make it permanent

    The artifact has a 7 day lease that each update renews. Open it in the hub and promote it, giving it its real name. Do this before sharing widely: renaming retires the old link.

  5. Update the same app

    Next month, say "Update the relstrat app with the new numbers". If Claude has lost track, ask it to list my Gizmos apps to recover the name and org. Permanent apps can also be edited in Gizmos Studio: ask Claude for the Studio link.

The temporary stage is the trap. A page shared as an artifact and never promoted disappears after 7 idle days, and the link stops working for everyone who bookmarked it. Promote first, then share.

  1. Open the repo in Claude Code

    At claude.ai/code pick the repository and start a session. Claude Code has the repo, your connectors and CLAUDE.md. Describe the change: a new page, a data refresh, a design fix.

  2. Let Claude Code build and verify

    It edits site/App.jsx, runs npm run build to prove the site compiles, and commits with a descriptive message on a feature branch.

  3. Open a pull request and merge

    Review the diff in GitHub. Ask Claude Code to open the PR if you want one. Merging to main is the publish action.

  4. GitHub Actions publishes

    The workflow installs dependencies, builds, previews the upload, and runs gizmos push with the version label set to the branch and commit. The Actions log shows the live URL. Typical run time is under two minutes.

  5. Nothing else

    Anyone with write access to the repo can now publish the same way. Use Run workflow with save when you want a version staged in Gizmos without going live, then make it live from the Versions tab.

Local check before merging: cd site && npm ci && npm run dev serves the dashboard at localhost:5173. Claude Code can run this and screenshot the result for you.

Step 9

The monthly update loop

This is what KPI tracking looks like once everything is in place. The first two steps are the same for everyone; only the publish step differs.

Each monthEasyIntermediateHard
1. Update the sourceAdd the new month to the workbook tabs. Update commentary in the Doc. Pull Tableau extracts if you use them.

Time per month20 to 30 minutes15 to 20 minutes10 to 15 minutes

Keep a changelog

Use the Gizmos version label for it: "Sep 2026 refresh" beats "v12". On the Hard route the commit message is the changelog.

Freeze the layout

Ask for data-only changes during refreshes. Save design changes for a separate session so a wrong number is never tangled up with a layout tweak.

Roll back without fear

Every route keeps versions. If a refresh is wrong, make the previous version live from the Versions tab, then fix the data.
